# pi-agent-core 问题与坑

## 🔴 高危坑点

### 1. 执行期间状态不一致

**问题**：Tool 执行期间，`messages` 数组只有 `assistant(toolCalls)`，没有 `toolResult`。

```
时间线:
T1: streamAssistantResponse 完成
    messages = [user, assistant(toolCalls)] ← toolResults 还没加！
    
T2: executeToolCalls 执行中
    messages 仍是 [user, assistant]
    
T3: 执行完成后
    messages = [user, assistant, toolResult]
```

**影响**：
- 如果 T2 崩溃，恢复后 LLM 会看到未完成的 toolCalls
- 可能导致 LLM 困惑或重试

**规避**：
- 使用 `sessionManager` 持久化状态（coding-agent 层实现）
- 崩溃后 `continue()`，让 LLM 自己处理

---

### 2. messages 是引用而非拷贝

**问题**：`currentContext.messages` 和 `this._state.messages` 是同一引用。

```typescript
// agent.ts _runLoop()
const context: AgentContext = {
    systemPrompt: this._state.systemPrompt,
    messages: this._state.messages.slice(), // 这里是浅拷贝！
    tools: this._state.tools,
};
```

但：

```typescript
// agent-loop.ts streamAssistantResponse()
context.messages.push(partialMessage); // 修改引用
```

**影响**：
- `context.messages` 和 `newMessages` 是独立数组
- 但 `context.messages` 会累积所有历史
- `newMessages` 只包含本轮新增

**关键区分**：
| 变量 | 用途 |
|------|------|
| `this._state.messages` | Agent 持久状态（UI 绑定） |
| `currentContext.messages` | 当前 LLM 调用的上下文 |
| `newMessages` | 本轮循环新增的消息（返回给调用者） |

---

### 3. continue() 的限制

**问题**：`continue()` 要求最后一条消息不能是 `assistant`。

```typescript
async continue() {
    if (messages[messages.length - 1].role === "assistant") {
        // 尝试先处理 steering/follow-up
        // 如果队列空，抛错
        throw new Error("Cannot continue from message role: assistant");
    }
    await _runLoop(undefined); // 继续
}
```

**场景**：
- LLM 返回了 toolCalls
- Tool 执行前崩溃
- 此时最后一条是 `assistant`
- `continue()` 会失败！

**解决**：
- 需要添加一条 `user` 消息或等待 `toolResult` 完成
- coding-agent 层可能通过 steering 处理

---

### 4. parallel 模式下的执行顺序

**问题**：`parallel` 模式启动是并行的，但**结果收集是顺序的**。

```typescript
// 并行启动
const runningCalls = runnableCalls.map(prepared => ({
    execution: executePreparedToolCall(prepared, ...), // 启动，不 await
}));

// 顺序等待
for (const running of runningCalls) {
    const executed = await running.execution; // 按数组顺序 await
    results.push(...);
}
```

**影响**：
- Tool A 和 B 同时启动
- 但如果 A 慢 B 快，仍会先等待 A 再收 B 的结果
- emit `tool_execution_end` 也是按原始顺序

**这不是真正的并行结果收集**，只是并行执行。

## 🟡 中等坑点

### 5. streamMessage 的生命周期

**问题**：`streamMessage` 只在流式期间存在，结束后立即为 `null`。

```typescript
// _processLoopEvent
case "message_end":
    this._state.streamMessage = null; // 立即清空
```

**影响**：
- 外部代码如果在 `message_end` 后访问 `streamMessage`，得到 `null`
- 需要自己在 `message_update` 时缓存 partial

---

### 6. abort() 不会立即停止

**问题**：`abort()` 只是设置 signal，不会立即停止执行。

```typescript
abort() {
    this.abortController?.abort(); // 只是发信号
}
```

**实际停止点**：
- `streamSimple` 内部检查 signal
- `executeToolCall` 内部检查 signal
- 循环中定期检查 `signal.aborted`

**影响**：
- Tool 执行可能不会立即中断
- 需要 Tool 内部配合检查 signal

---

### 7. beforeToolCall 拦截后的处理

**问题**：`beforeToolCall` 返回 `{ block: true }` 后，会生成 error tool result。

```typescript
if (preparation.blocked) {
    // 生成 error result，而不是跳过
    results.push({
        content: [{ type: "text", text: reason }],
        isError: true,
    });
}
```

**影响**：
- 拦截不是"忽略"，而是"返回错误"
- LLM 会看到这个错误，可能影响后续行为

---

### 8. steering 和 follow-up 的混淆

| 特性 | steering | follow-up |
|------|----------|-----------|
| 添加时机 | Agent 运行时 | Agent 运行时 |
| 执行时机 | 当前回合结束后 | Agent 即将停止时 |
| 触发条件 | 有 tool calls 完成 | 无 tool calls 且无 steering |
| 用途 | 打断当前流程 | 追加任务 |

**常见错误**：
- 用 `steer()` 想追加任务 → 会在当前回合后执行，可能不是预期
- 用 `followUp()` 想打断 → 可能很久后才执行

---

## 🟢 低危但易错

### 9. message_update 只针对 assistant

**问题**：`message_update` 事件只用于 assistant 消息流式更新。

```typescript
// _processLoopEvent
case "message_update":
    // 没有 role 检查，但只有 assistant 会触发
```

**影响**：
- User 消息不会触发 `message_update`
- ToolResult 也不会

---

### 10. TokenUsage 统计时机

**问题**：Token 使用统计在 `message_end` 时才可用。

```typescript
// streamAssistantResponse
case "done":
    finalMessage.usage = ... // 此时才有统计
```

**影响**：
- `message_start` 和 `message_update` 期间 usage 为 0
- 需要在 `message_end` 后读取

---

### 11. pendingToolCalls 的并发问题

**问题**：`pendingToolCalls` 是 Set，但事件处理是同步的。

```typescript
// tool_execution_start
pendingToolCalls.add(event.toolCallId);

// tool_execution_end
pendingToolCalls.delete(event.toolCallId);
```

**潜在问题**：
- 如果 emit 是异步的，可能有竞态
- 但实际 `_processLoopEvent` 是同步处理

---

### 12. convertToLlm 的契约

**问题**：`convertToLlm` 必须处理所有 `AgentMessage` 类型。

```typescript
convertToLlm: (messages) => messages.filter(m => 
    m.role === "user" || m.role === "assistant" || m.role === "toolResult"
)
```

**常见错误**：
- 忘记过滤 custom 消息 → LLM 报错
- 返回空数组 → LLM 调用失败

---

## 📝 调试技巧

### 查看当前状态

```typescript
agent.subscribe(event => {
    console.log("Event:", event.type);
    console.log("State:", {
        isStreaming: agent.state.isStreaming,
        streamMessage: agent.state.streamMessage?.role,
        pendingToolCalls: [...agent.state.pendingToolCalls],
        messageCount: agent.state.messages.length,
    });
});
```

### 追踪消息流向

```typescript
agent.subscribe(event => {
    if (event.type === "message_start") {
        console.log("→ Start:", event.message.role);
    }
    if (event.type === "message_end") {
        console.log("→ End:", event.message.role);
    }
    if (event.type === "tool_execution_start") {
        console.log("🔧 Tool:", event.toolName);
    }
    if (event.type === "tool_execution_end") {
        console.log("✓ Tool done:", event.toolCallId);
    }
});
```

### 检查状态一致性

```typescript
function checkStateConsistency(agent) {
    const state = agent.state;
    
    // 1. streaming 时应有 streamMessage
    if (state.isStreaming && state.streamMessage === null) {
        console.warn("Inconsistent: streaming but no streamMessage");
    }
    
    // 2. 非 streaming 时不应有 streamMessage
    if (!state.isStreaming && state.streamMessage !== null) {
        console.warn("Inconsistent: not streaming but has streamMessage");
    }
    
    // 3. pendingToolCalls 应非空时 isStreaming 应为 true
    if (state.pendingToolCalls.size > 0 && !state.isStreaming) {
        console.warn("Inconsistent: has pending tools but not streaming");
    }
}
```
