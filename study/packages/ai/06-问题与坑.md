# pi-ai 问题与坑

## 1. 浏览器兼容性

### 1.1 CSP 限制 (浏览器扩展)

**问题**：Chrome 扩展 Manifest V3 禁止使用 `eval` 和 `Function` 构造器。

**影响**：
- AJV 验证器无法编译 schema（需要 `new Function()`）
- 工具参数验证被完全跳过

**解决方案**：
```typescript
// validation.ts:15
const isBrowserExtension = typeof globalThis !== "undefined" && 
  (globalThis as any).chrome?.runtime?.id !== undefined;

function canUseRuntimeCodegen(): boolean {
  if (isBrowserExtension) return false;
  try {
    new Function("return true;");
    return true;
  } catch {
    return false;
  }
}

// 在浏览器扩展中直接返回原始参数，跳过验证
if (!ajv || !canUseRuntimeCodegen()) {
  return toolCall.arguments;  // 不验证！
}
```

**坑点**：浏览器扩展中工具参数可能不符合 schema，需要自行验证或信任 LLM。

---

### 1.2 Node.js 模块动态导入

**问题**：在浏览器/Vite 构建中直接导入 `node:fs` 会导致错误。

**影响**：
- `env-api-keys.ts` 需要动态导入 Node.js 模块

**解决方案**：
```typescript
// env-api-keys.ts - 永远不要转换为顶层导入！
let _existsSync: typeof import("node:fs").existsSync | null = null;

if (typeof process !== "undefined" && (process.versions?.node || process.versions?.bun)) {
  dynamicImport("node:fs").then((m) => {
    _existsSync = (m as typeof import("node:fs")).existsSync;
  });
}
```

**坑点**：异步导入存在竞态条件，首次调用时模块可能尚未加载。

## 2. 异步与竞态条件

### 2.1 EventStream 的竞态条件

**问题**：多个 consumer 同时迭代同一个流会怎样？

**答案**：
```typescript
// EventStream 的 asyncIterator 支持多消费者
async *[Symbol.asyncIterator](): AsyncIterator<T> {
  while (true) {
    if (this.queue.length > 0) {
      yield this.queue.shift()!;
    } else if (this.done) {
      return;
    } else {
      // 每个消费者有自己的 waiter
      const result = await new Promise<IteratorResult<T>>(
        (resolve) => this.waiting.push(resolve)
      );
      if (result.done) return;
      yield result.value;
    }
  }
}
```

**坑点**：虽然支持多消费者，但事件只会被第一个等待的消费者获取。

---

### 2.2 懒加载的竞态条件

**问题**：多次快速调用同一 Provider 会重复加载吗？

**答案**：不会，使用 Promise 缓存：
```typescript
let anthropicProviderModulePromise: Promise<...> | undefined;

function loadAnthropicProviderModule() {
  // ||= 确保只创建一次 Promise
  anthropicProviderModulePromise ||= import("./anthropic.js").then(...);
  return anthropicProviderModulePromise;
}
```

**坑点**：如果首次加载失败，Promise 会保持 rejected 状态，后续调用都会失败。

## 3. Provider 差异

### 3.1 消息格式差异

| Provider | 系统提示 | 工具结果格式 | 图像输入 |
|----------|----------|--------------|----------|
| OpenAI | `system` 角色 | 需要 `name` 字段 | base64 |
| Anthropic | `system` 参数 | 不需要 `name` | base64 |
| Google | `system_instruction` | Content parts | InlineData |
| Mistral | `system` 角色 | 类似 OpenAI | URL |

**坑点**：`transform-messages.ts` 需要处理各种差异。

---

### 3.2 Token 计算差异

**问题**：不同 Provider 的 usage 统计方式不同。

| Provider | 流式中 usage | cacheRead | cacheWrite |
|----------|-------------|-----------|------------|
| OpenAI | chunk.usage | ✅ | ❌ |
| Anthropic | message_start + message_delta | ✅ | ✅ |
| Google | usageMetadata | ❌ | ❌ |
| Mistral | ❌ | ❌ | ❌ |

**坑点**：某些 Provider 流式响应中没有 usage，成本计算可能不准确。

---

### 3.3 Reasoning/Thinking 差异

**问题**：不同 Provider 的推理/思考实现不同。

| Provider | 参数名 | 参数值 | 输出位置 |
|----------|--------|--------|----------|
| OpenAI | `reasoning_effort` | "low"/"medium"/"high" | `reasoning_content` |
| Anthropic | `thinking` + `budget_tokens` | 对象 | `thinking` blocks |
| Google | `thinkingConfig` | 对象 | `thought` |
| OpenRouter | `reasoning.effort` | 嵌套对象 | `reasoning` |
| xAI | `enable_thinking` | boolean | - |

**坑点**：`OpenAICompletionsCompat` 需要大量兼容性配置。

---

## 4. 流式处理陷阱

### 4.1 流式 JSON 解析

**问题**：工具调用参数是流式返回的 JSON 片段。

**解决方案**：
```typescript
import { parseStreamingJson } from "./utils/json-parse.js";

// 在 toolcall_end 时解析
block.arguments = parseStreamingJson(block.partialArgs);
```

**坑点**：
- 解析失败时返回 `{}`，不是抛出错误
- 部分解析的 JSON 可能不完整

---

### 4.2 SSE 解析陷阱

**问题**：不同 Provider 的 SSE 格式略有不同。

**坑点**：
- 某些 Provider 在 data 前有空格：`data: {...}` vs `data:{...}`
- 某些 Provider 有多行 data：`data: {...}\ndata: {...}`
- 心跳注释：`:` 开头的行应忽略

---

### 4.3 AbortSignal 行为

**问题**：取消请求后流会怎样？

**答案**：
```typescript
// OpenAI SDK 示例
const stream = await client.chat.completions.create(
  params, 
  { signal: options?.signal }
);

// signal abort 时
// 1. fetch 请求被取消
// 2. for await 抛出 AbortError
// 3. catch 块捕获，发送 error 事件
```

**坑点**：某些 Provider 可能不支持 AbortSignal，需要手动处理。

---

## 5. 工具调用陷阱

### 5.1 工具参数验证失败

**问题**：LLM 生成的参数可能不符合 schema。

**解决方案**：
```typescript
try {
  const validatedArgs = validateToolCall(tools, toolCall);
} catch (error) {
  // 返回错误给 LLM
  const toolResult: ToolResultMessage = {
    role: "toolResult",
    toolCallId: toolCall.id,
    toolName: toolCall.name,
    content: [{ type: "text", text: error.message }],
    isError: true,
    timestamp: Date.now()
  };
}
```

**坑点**：AJV 的类型强制可能导致意外行为（如 `"123"` → `123`）。

---

### 5.2 并发工具调用

**问题**：某些 Provider 支持单次响应多个工具调用。

**状态**：pi-ai 目前串行处理工具调用。

**坑点**：
- `parallel_tool_calls` 参数未暴露
- 某些场景下并行执行会更高效

---

### 5.3 工具调用后的消息格式

**问题**：不同 Provider 对工具调用后的消息格式要求不同。

| Provider | 要求 |
|----------|------|
| OpenAI | `tool` 角色消息必须紧跟 assistant 的 tool_calls |
| Anthropic | tool_use + tool_result 成对出现 |
| Google | functionResponse content |

**坑点**：`transform-messages.ts` 需要处理这些差异。

---

## 6. OAuth 陷阱

### 6.1 Token 过期处理

**问题**：Token 在请求过程中过期怎么办？

**答案**：pi-ai 不自动刷新 Token，需要用户处理：
```typescript
const { newCredentials, apiKey } = await getOAuthApiKey("anthropic", credentials);
// 如果 newCredentials !== credentials，需要保存新凭证
```

**坑点**：长对话中 Token 可能在中间过期。

---

### 6.2 GitHub Copilot 特殊处理

**问题**：GitHub Copilot 需要特殊的 header 和 token 派生。

**解决方案**：
```typescript
// github-copilot-headers.ts
export function buildCopilotDynamicHeaders(
  credentials: OAuthCredentials
): Record<string, string> {
  // 派生 token
  const editorToken = deriveToken(credentials.accessToken);
  return {
    "authorization": `token ${editorToken}`,
    "editor-version": "vscode/1.85.0",
    // ...
  };
}
```

**坑点**：header 格式与其他 Provider 完全不同。

---

### 6.3 OAuth 设备 flow 超时

**问题**：用户没有及时在浏览器授权怎么办？

**答案**：
```typescript
// 默认超时 5 分钟
const expiresIn = 300; // seconds

// 轮询间隔
const interval = 5; // seconds
```

**坑点**：某些 Provider 的超时时间不同。

---

## 7. 模型配置陷阱

### 7.1 models.generated.ts 的生成

**问题**：模型配置是自动生成的，如何更新？

**答案**：
```bash
cd packages/ai
npm run generate-models
```

**坑点**：
- 需要各 Provider 的 API 访问权限
- 生成过程可能失败（网络/API 限制）

---

### 7.2 模型 capability 检测

**问题**：如何判断模型支持哪些功能？

**当前方案**：
```typescript
const model = getModel("openai", "gpt-4o");

// 检查 reasoning
if (model.reasoning) { ... }

// 检查图像输入
if (model.input.includes("image")) { ... }

// 检查 xhigh thinking
if (supportsXhigh(model)) { ... }
```

**坑点**：某些功能需要运行时检测（如 tool calling）。

---

## 8. TypeScript 类型陷阱

### 8.1 泛型推导问题

**问题**：`getModel` 返回的类型推导可能不准确。

```typescript
// 理想情况
const model = getModel("openai", "gpt-4o");
// model: Model<"openai-completions">

// 实际情况：可能返回 Model<string>
```

**解决方案**：显式类型断言。

---

### 8.2 模块导出循环依赖

**问题**：`index.ts` 和 `stream.ts` 可能产生循环。

**解决方案**：
```typescript
// stream.ts
import "./providers/register-builtins.js";  // 直接导入执行副作用
```

**坑点**：模块加载顺序可能影响 Provider 注册。

---

## 9. 性能陷阱

### 9.1 大上下文处理

**问题**：大上下文（>100K tokens）可能导致性能问题。

**建议**：
- 使用 `cacheRetention` 启用缓存
- 定期清理不必要的消息历史
- 监控 `usage.totalTokens`

---

### 9.2 内存泄漏风险

**问题**：EventStream 可能长时间存活。

**潜在问题**：
```typescript
const stream = stream(model, context);

// 忘记迭代或等待 result
// stream 会一直占用内存等待消费
```

**解决方案**：始终消费流或使用 AbortSignal 取消。

---
